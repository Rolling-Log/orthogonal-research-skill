# orthogonal-research-skill

执行“建档 → 海内外研究 → 双轴分析 → 对抗审查 → 可视化 → 写作 → PDF → 逐页验收”。以横纵分析 v1 为最低能力基线；本版增加的证据台账、全球检索、图表、知识图谱、失败披露和跨平台构建只能叠加，不能替换或缩减基线能力。

## 先读取必要资源

1. 每次研究先读取 [research-protocol.md](references/research-protocol.md)。
2. 需要写作、格式或来源结构时读取 [report-spec.md](references/report-spec.md)。
3. 需要图表、图谱或图片时读取 [visual-system.md](references/visual-system.md)。
4. 进入交付前读取 [adversarial-review.md](references/adversarial-review.md) 和 [v1-regression-matrix.md](references/v1-regression-matrix.md)。
5. 需要可复制输入时读取 [examples.md](references/examples.md)。这些方法已经集成在本 Skill 中，不要求安装或调用其他 Skill。

## 建立研究状态与交付目录

用户未指定输出目录和输出文件时，第一步必须运行以下命令，在系统桌面创建唯一的带时间戳研究包；不得先在当前工作目录创建报告：

```text
python <skill-dir>/scripts/init_workspace.py --subject "对象"
```

读取命令返回 JSON 中的 `workspace` 绝对路径，并把它作为后续写入、下载图片、渲染和构建的工作目录。用户明确指定目录时传入 `--destination "用户目录"`，并以用户要求为准；用户明确指定单个文件或平铺方式时，覆盖默认分装。不得覆盖已有目录，也不得把最终产物散落在研究包之外。默认结构为：

```text
<对象>_横纵分析报告_<日期时间>/
├── report.md
├── <对象>_横纵分析报告.pdf
├── sources/
│   ├── sources.json
│   └── research-log.json
├── data/
├── visuals/
├── images/
└── build/
    ├── report.html
    ├── report.build.json
    └── qa/
```

将 `sources/sources.json` 作为来源真相表，`data/` 作为数据真相表，`report.md` 只引用稳定相对路径。所有临时文件和质检截图进入 `build/`。来源 ID 固定为 `S001`、`S002`……；重跑时复用，不重新编号。记录研究对象、类型、研究动机、特别关注点、全球或指定地域、研究截面日期。用户已给足信息时直接执行；只有缺失信息会实质改变边界时才追问。

## 第一步：联网收集海内外证据

必须使用当前环境可用的联网能力核验事实，不能仅靠模型记忆写报告。搜索摘要只用于发现线索，必须打开原始页面或文档。

**联网容错**：优先使用当前环境提供的联网工具打开原始页面；需要脚本化获取时使用 Python 标准库，并遵守环境已配置的代理和 TLS 校验。不要关闭证书校验、绕过访问控制或把凭据写入 URL/日志。联网连续失败时，标记受阻域名、尝试过的替代来源和受影响结论，降低相应置信度并在执行摘要和“研究范围与限制”中披露。
### 并行研究策略

环境允许且对象复杂时并行分成三组；环境不允许时按相同标准顺序执行：

- 纵向组：起源、创始团队、首次发布、版本、融资、技术/组织/战略转向、危机与当前状态；
- 横向组：竞品候选、官方定位、价格与规模、独立评测、真实社区反馈、市场结构；
- 补充组：原论文、监管/财务文件、创始人深度背景、行业环境、量化数据与图片授权。

每组都返回原始 URL、来源 ID、关键事实、原始口径、时间范围、冲突点和不确定性。合并时去掉转载造成的循环印证。

### 全球检索最低要求

- 全球性对象至少执行中文和英文两套检索；主要海外玩家再补充其官方语言或当地权威来源。
- 每种语言、每条研究轴至少使用三组不同关键词。不要只换同义词，要覆盖起源、演进、规模、竞品、口碑、风险和未来。
- 学术、算法、模型和技术范式必须定位原论文，优先 arXiv、Crossref、PubMed、会议论文集或出版方页面；引用预印本时说明状态。
- 每个主要竞品至少取得一手资料、独立媒体/研究资料和真实社区反馈。社区样本不可外推为全部用户。
- 全球性报告默认目标为不少于 20 个独立来源，其中不少于 8 个一手来源、5 个海外来源。目标未达到不能静默结束。
- 连续两轮检索都没有新增关键事件、主要竞品、关键数据或反证，才可判断接近饱和。

### 来源优先级

1. 官方公告、文档、财报、监管文件、标准、论文、代码仓库、原始数据库；
2. 有原创采访或原始数据的权威媒体、研究机构和行业组织；
3. 可归因的专家评论、GitHub Issues、Reddit、论坛、X、知乎等社区材料；
4. 聚合、转载和 SEO 页面仅作发现线索，不独立支撑关键主张。

日期、版本、价格、融资、营收、用户数和份额优先用一手来源。高影响结论用两个独立来源交叉核验。区分事实、来源观点、分析推断和未来假设；不把估值当营收，不把注册用户当活跃用户，不把公司目标当已实现结果。

### 文化语言来源平衡

研究开始时在 `coverage.target_perspective_groups` 确定 2–4 个“语言＋主要地区文化语境”组。每条来源必须填写 `language`、`region` 和 `perspective_group`。只用最终实际引用、彼此独立且属于 Tier 1–3 的来源计算占比；翻译稿、转载或同一通讯社衍生稿通过 `independence_key` 合并，并归入原始发布者的语境。每组占比必须在 20%–80% 之间，包含边界值。

不得用低质量或无关来源凑比例。客观资料稀缺或网络受阻时继续补充检索；仍无法满足时，在 `coverage.balance_exception` 和 `limitations` 记录原因、尝试、偏差、受影响结论与低/中置信度，并在执行摘要和“研究范围与限制”披露。没有完整例外记录时，失衡即视为研究失败。

### 事实溯源与论据约束

- 一手来源优于二手来源：官方博客、公告、财报、监管文件和原论文，优先于权威媒体原创报道；原创报道优先于转载或聚合。
- 每个关键事实必须能回到 `sources.json` 中的可靠来源。高影响事实不可只靠单一二手来源；若只能取得一个来源，必须在正文标明证据局限并降低置信度。
- 搜不到的信息写“公开信息暂缺”或“截至研究截面暂缺可靠公开资料”，绝不根据常识、搜索摘要或相邻事实补写。
- 观点必须先摆事实，再给判断。使用“我觉得”“我的判断是”“更可能的解释是”等承认主观性的姿态，并紧跟支持证据、反证和适用边界；不要把来源观点改写成作者定论。
- 文末“信息来源与方法说明”列出所有实际引用来源的全名、发布者、完整 URL、发布日期和访问日期，不得用搜索结果页代替原始页面。

### 搜索覆盖状态

在 `sources.json.coverage` 记录：尝试语言、地区和平台，成功来源类别与域名，受阻域名、网络限制、替代检索和证据缺口。`limitations` 逐条写明影响到的章节、结论与置信度。海外搜索失败时，报告必须明确：缺了什么、为什么缺、可能偏向何种叙事、哪些判断因此降级。

### 信息充分性闸门

进入写作前同时确认：

- 纵向能讲出起源、推动者、阶段变化、关键决策、路径依赖、危机与现状的完整故事；
- 横向候选池无明显全球玩家遗漏，竞品选择有理由，比较口径一致；
- 每个主要竞品有官方视角、独立视角和用户视角；
- 图表数据有单位、币种、统计期、地域、样本、定义和来源 ID；
- 核心主张可追溯，来源冲突已解释，关键反证已主动寻找；
- 图片来源、作者/机构、许可或截图日期均已记录。
- 所有关键事实均已标注来源；无可靠来源的信息均已写明“公开信息暂缺”，没有编造。

未通过就补充研究；客观受阻时披露限制，绝不猜测填洞。

## 第二步：纵向分析

沿时间轴还原对象从诞生到研究截面的完整生命历程。用“背景约束 → 选择 → 结果 → 新约束”构成因果叙事，不写发布记录流水账。

必须覆盖：

- 起源背景、前身、创始团队/提出者的经历与动机，以及为什么是他们在那个时间点做这件事；
- 明确的成立、首次发布或首次提出节点，最初形态与今天的差异；
- 版本、融资、组织、技术路线、商业模式、合作/收购、增长、争议和危机；
- 每个关键节点为何选 A 不选 B，当时约束、备选方案、权衡和信息条件；
- 早期选择如何形成技术栈、生态、渠道、品牌或组织上的路径依赖；
- 3–6 个自然阶段，每阶段的核心特征、核心矛盾和转折条件。

将 5–10 个真正改变方向的节点做成时间线；历史图片只在能解释阶段变化时使用。纵向正文 6,000–15,000 中文字，历史越长越接近上限。

## 第三步：横向分析

以研究截面为同一时间切片。先建立候选池，再按需求重叠、资源竞争和战略参照选择对象。

- 场景 A，无直接竞品：解释无竞品是因为品类新、壁垒高还是市场小；比较间接替代、上一代方案和潜在进入者。
- 场景 B，1–2 个竞品：逐一深挖，不用空泛总表代替分析。
- 场景 C，3 个以上：选 3–5 个最有代表性的对象深入比较，其余简述并说明未入选原因。

统一地区、币种、税费、档位、版本、统计期和用户定义，覆盖技术/方法、产品形态、体验、目标用户、价格、商业模式、组织、规模、优势、短板、用户口碑和生态位。参数表之后必须说明“各自活成了什么样、用户为何选择、实际代价是什么”。

分析整个赛道是百花齐放、双强、寡头还是单极，研究对象填补了什么空白，与谁直接争夺资源，机会与风险如何变化。横向正文 3,000–10,000 中文字；场景 C 的每个主要竞品原则上不少于 1,500 字。

## 第四步：横纵交汇

交汇不是摘要。至少形成三条无法由单轴直接得到的判断，并回答：

1. 哪些历史事件和选择决定了今天的竞争位置；
2. 主要竞品的起源与演进路径为何不同，这些差异如何变成今天的产品和组织特征；
3. 每项核心优势能追溯到哪个节点，持续条件是什么；
4. 每项核心劣势或包袱源自哪个旧决策，当年的好选择为何可能失效；
5. 最可能、最危险、最乐观三个剧本的机制、时间范围、触发信号、反证与监测指标。

交汇正文 1,500–3,000 中文字。明确标记“事实”“判断”“假设”，避免把相关性写成因果。

## 第五步：可视化与图片

先把结构化数据写入 `data/visuals.json`，再运行：

```text
python <skill-dir>/scripts/render_visuals.py data/visuals.json --output-dir visuals
```

支持 `timeline`、`bar`、`line`、`donut`、`matrix`、`knowledge_graph`。最终 Markdown/PDF 只嵌入已渲染 SVG、PNG 或 JPEG，不留下 Mermaid、DOT、Vega、图表代码或 XML。所有图必须有结论型标题、统计时间、单位、口径、来源 ID和正文解读。无可靠数据时用定性矩阵或表格，不造数。

知识图谱先提取“实体—关系—实体”三元组。默认 8–18 个节点、一个中心、2–4 层；事实边为实线，假设边为虚线并标注。每条边带来源 ID。过密就按人物/产品/技术/商业生态拆图，不把乱码、代码或交互组件截图当图谱。

全文通常使用 4–10 张真实图片、3–7 张数据图、1–3 张图谱，但数量服从信息密度。产品报告至少嵌入 2 张能帮助理解产品形态或使用方式的真实产品图、官方界面截图或公开演示截图；只有确实无法取得可用且权属清楚的素材时才允许缺省，并在“研究范围与限制”说明，不得静默省略。优先官方截图/媒体资产、财报原图、论文图或许可明确的 Wikimedia Commons 图片。不得把 AI 图冒充历史照片、产品截图或事实证据。位图插图和产品截图以约 72%–80% 正文宽度居中，避免打断阅读；数据图、时间线、矩阵和知识图谱保持原有全宽与可读字号，不随插图缩小。

### 图片下载容错

下载图片时优先使用当前环境的联网工具或 Python `urllib.request`，保留原始 JPEG/PNG 或使用环境已有的图像工具处理尺寸。任何替代 URL、转换、压缩或截图都要记录来源、作者/机构、许可和访问日期。若下载失败，标记该图片为“不可获取”，在“研究范围与限制”中披露缺失，不静默省略。

## 第六步：叙事写作、读者流与主结构

维持“研究严谨 + 深度可读性”：叙事驱动、长短句有节奏、层层剥开、知识自然带入、先摆事实再敢下判断、前文伏笔在交汇处回环。判断使用“我的判断是”等承认主观性的表达，并给出证据链。最终报告不得出现方法论创作者姓名、账号名、个人署名或人物化文风标签；方法说明只描述横纵分析法本身。

分两遍完成写作。第一遍写证据稿，锁定事实、判断、反证和来源映射；第二遍写阅读稿，只调整叙事顺序、段落长度、转场和措辞，不改变事实或引用。以非虚构书稿为主，只吸收公众号文章的推进感：每个小节自然形成“具体事实或场景 → 核心问题 → 证据展开 → 作者判断 → 通往下一节的桥梁”，不得虚构场景或悬念。

一个段落只承担一个主要观点，常规段落以约 80–220 个汉字为主，超过 300 字优先拆段。连续数据、定义和方法细节移入表格、图注或段后说明；引用集中在句末或段末，相邻事实由同一组来源支撑时合并引用。每个主要章节至少有一个自然开场和一个承上启下的收束，避免连续堆叠标题、表格或结论摘要。

克制公众号式强口语，不使用三连尾部。禁止“首先/其次/最后”“综上所述”“值得注意的是”“赋能”“抓手”“打造闭环”等套话；避免空泛的“某 AI 工具”。搜不到就写“公开信息暂缺”，不能编造。

报告正文按以下主结构写，不生成目录：

1. 一句话定义；
2. 纵向分析：从诞生到当下；
3. 横向分析：竞争图谱；
4. 横纵交汇洞察；
5. 信息来源与方法说明。

在“一句话定义”后可插入 300–600 字执行摘要与“研究范围与限制”；在相应章节内插入时间线、数据图和知识图谱。不要让增强模块改变上述主干顺序。全文 10,000–30,000 中文字，不以压缩为目标，不重复凑字数。

对象适配：产品重版本/路线/体验/价格；公司重团队/融资/组织/商业模式；概念重提出者/传播/争论/相近概念；人物重经历/关键决策/言论变化/同领域路线差异。

### 正文强调语法

正文必须适量使用标准 `**加粗**` 和固定语义色突出真正影响理解的关键信息：`[[blue:关键判断或关键数据]]`、`[[green:正向信号]]`、`[[purple:概念或方法]]`、`[[red:已证实的风险警告]]`。受控换色在 PDF 中同时加粗；每个主要章节至少使用一次，但每段原则上不超过 1–2 处，不给整段换色，不混合嵌套，也不以颜色代替证据。PDF 固定使用 v1 配色：H1 `#1A5276`、H2 `#1E8449`、H3 `#2E86C1`、H4 `#5B2C6F`、正文 `#2C3E50`。正文中的主要章节标题使用 `##`，构建后左侧显示 3pt 深蓝小竖条。

## 第七步：紧凑编号引用与编号文献

只在需要补充来源、口径、方法或推断边界的句子或段落末尾使用：

```markdown
该阶段完成了渠道转向。{{@S014,@S019 | 统计口径为官方披露的付费企业客户，不含试用账户。}}
```

内部 `S###` 不显示在最终 PDF。构建器按来源首次出现顺序生成连续编号，在标记位置只显示紧凑的深蓝上标 `[1][2]`；来源简称、年份和完整信息集中到文末参考文献。确有必要的口径、方法或边界说明放在对应段落下方的浅灰蓝“说明”行，不再挤进右上角。正文始终全宽，同一来源全文只使用一个编号。每条来源必须在 `sources/sources.json` 提供 `display_name`；引用不存在的 ID 时构建失败。说明尽量控制在 10–45 个汉字，长解释放回正文或“研究范围与限制”。

文末按首次引用顺序写连续编号来源，格式为 `1. 来源简称｜发布者｜完整标题｜URL｜发布日期：YYYY-MM-DD｜访问日期：YYYY-MM-DD`。正文、图表、图谱或图注引用的每个来源必须恰好对应一条文末记录；文末记录也必须在报告中实际使用。缺号、重号、顺序错误、错误 URL、未使用来源或遗漏来源均构建失败。不要使用旧式“方括号＋@来源 ID”标记。

## 第八步：构建 PDF

使用同一条命令兼容 macOS、Windows PowerShell 与 CMD：

```text
python <skill-dir>/scripts/build_report.py report.md "对象_横纵分析报告.pdf" --title "对象" --sources sources/sources.json --visual-spec data/visuals.json --html-output build/report.html --log-output build/report.build.json
```

构建器要求 Python 3.9+，其余 PDF 依赖与中日韩字体已经随 Skill 携带。它直接生成 PDF，同时输出 HTML 调试稿和 `.build.json` 日志；HTML 失败不得影响 PDF 判定。无需系统字体、浏览器、图形命令行程序或平台专属包管理器。

构建器支持本地 JPEG、非交错 8-bit PNG，以及由 `visuals.json` 生成的 SVG。WebP、AVIF、交错 PNG 或无法匹配视觉规范的任意 SVG 会在构建前给出转换/修复提示。所有路径必须相对报告目录；禁止远程图片和临时绝对路径。

运行内置自检：

```text
python <skill-dir>/scripts/init_workspace.py --self-test
python <skill-dir>/scripts/build_report.py --self-test
```

## 错误处理与降级

- 来源冲突：并列口径，解释时间、定义与利益立场；无法裁决则标“待验证”。
- 登录墙/付费墙：寻找同一事实的一手公告或合法替代，不绕过访问控制。
- 海外网络受阻：记录域名和尝试，寻找合法镜像/监管/学术替代，并披露偏差与置信度。
- 来源文化语言占比失衡：继续检索；无法补齐时完整记录例外、披露偏差并降低置信度，不用 Tier 4 或重复转载凑数。
- 引用与文末编号不一致：修复首次引用顺序、URL 或缺失来源；不得跳过构建校验。
- 无量化数据：改用定性矩阵或表格；不生成伪图。
- 图片缺失或授权不明：删除或替换，不能留下破图。
- 图谱过密：拆图；保留中心和高信息量关系。
- 中文乱码、编号角标重叠、表格断裂：视为构建失败，调整后重新渲染。
- PDF 构建失败：保留 Markdown、SVG、HTML 和日志，报告明确错误；不得声称已交付 PDF。

## 第九步：第一性原理与对抗式验收

报告价值取决于“覆盖广度 × 证据可靠度 × 因果深度 × 阅读清晰度 × 可复现性”；任一项接近零，堆字数也不能补救。按 [adversarial-review.md](references/adversarial-review.md) 完成五轮反方审查：海外遗漏、关键事实反证、竞品口径、因果跳跃、跨平台渲染。

交付前执行：

1. 对照 [v1-regression-matrix.md](references/v1-regression-matrix.md)，每一项必须标“保留”或“增强”并有证据；
2. 运行 `init_workspace.py --self-test`、`render_visuals.py` 和 `build_report.py --self-test`；
3. 完成读者流审查，检查突兀转场、重复解释、主语漂移、长句堆叠、证据打断叙事和章节之间缺少因果桥梁；
4. 构建真实报告，将 PDF 每页渲染成图片，逐页检查封面不显示作者、主章节标题左侧 3pt 深蓝小竖条、全宽正文、中文、3pt 深蓝竖线浅灰底引用块、图注层级、正文强调、紧凑编号角标与段后说明、表格、真实图片/截图、图表、图谱、页眉页脚、孤行和分页；
5. 核对所有关键事实均有来源，正文/图表引用与文末编号一一对应，文化语言组在 20%–80% 或已完整披露例外；数据、图注、来源和截面日期一致，搜不到的信息已标注“公开信息暂缺”；
6. 交付整个分装研究包，并如实说明限制。除用户明确要求外，不把单个文件散落到包外；未指定路径时，交付前必须确认最终 PDF 的绝对路径位于命令返回的桌面 `workspace` 中并向用户给出该路径。

当前包只有在真实对应系统运行并留下自检日志后，才能声称该系统实机通过；仅做路径/编码模拟时必须标注“静态兼容，未实机验证”。任何验收项未通过都不能称为完成。
