# 报告结构、文风与构建规范

## 不可改变的报告主干

封面之后按以下顺序写正文，不生成目录页：

1. 一、一句话定义；
2. 二、纵向分析：从诞生到当下；
3. 三、横向分析：竞争图谱；
4. 四、横纵交汇洞察；
5. 五、信息来源与方法说明。

执行摘要与“研究范围与限制”放在“一句话定义”之后；知识图谱、图表和本章判断嵌入最相关章节，不新建会打断主线的大段附录。

篇幅下限：纵向 6,000–15,000 字；横向 3,000–10,000 字；交汇 1,500–3,000 字；全文 10,000–30,000 字。信息不足时披露，不用同义反复凑字数。

## v1 视觉基线

- A4；上边距 25mm，左右 20mm，下边距 20mm；正文使用全部可用宽度；
- 封面标题 28pt 深蓝 `#1A5276`，副标题“横纵分析法深度研究报告”；
- 一级深蓝、二级绿色 `#1E8449`、三级浅蓝 `#2E86C1`、四级紫色 `#5B2C6F`；
- 报告主章节使用 Markdown `##`，其标题左侧显示 3pt 深蓝小竖条；封面标题不加竖条；
- 正文 10.5pt、1.75 倍行距、深灰 `#2C3E50`；
- 引用块为左侧 3pt 深蓝 `#1A5276` 竖线与浅灰 `#F4F6F7` 背景；
- 表格全宽，深蓝表头白字，偶数行浅灰；
- 正文页眉“报告标题 | 横纵分析法深度研究报告”，页脚“第 X 页”；封面不显示；
- 封面显示报告标题、副标题、生成日期、全文字数和预计阅读时间，不显示作者姓名；`--author` 如使用，仅写入 PDF 元数据。

### 封面统计（V2.1）

每份报告的 PDF 与 HTML 封面都由构建器自动显示“全文字数”和“预计阅读时间”；不要由模型估算或在 Markdown 中手工填写。内容改动后重新构建，统计同步更新，并保存到构建日志的 `reading_metrics`。

字数口径：汉字各计 1，外文单词和数字串各计 1；包含正文、章节标题、表格、图注、段后说明、参考文献及实际嵌入的矢量图文字。不计封面、重复页眉页脚、标点、空白、URL、引用编号、Markdown 语法、图片路径和位图内文字。封面称“全文字数”，以上口径用于避免把来源地址和排版代码算成阅读内容。

预计阅读时间采用中文报告的 300 至 500 字/分钟粗估范围，向上取整至分钟。此速度是明确的估算假设，不是适用于所有读者的实测标准；图表研读、查证和思考另计，不代表理解或掌握所需时间。封面显示范围及粗估依据，不假装精确到秒。

只微调字距、留白、图注、分页和中英文混排。不要把正文缩成窄栏，不以黑色超大标题或红蓝品牌色取代 v1 配色。

## 紧凑编号引用与文末编号

语法：

```markdown
这项转型依赖更早的模块化选择。{{@S014,@S019 | 两家公司披露的周期定义不同，因此只比较方向。}}
```

构建结果：按来源首次出现顺序生成连续编号，在标记所在句子或段落末尾只显示紧凑的深蓝 `#1A5276` 上标 `[1][2]`。来源简称、年份和完整信息集中在文末；标记中的解释若非空，则在对应段落下方显示浅灰蓝的“说明：[1][2] ……”行。最终 PDF 不显示内部 `S###`，正文始终保持全宽。

同一语法适用于正文段落、引用块、列表项、表格单元格及 `<span class="figure-source">…</span>` 图来源说明。列表解释跟在对应项之后；表格解释留在对应单元格中；图来源解释跟在来源说明之后。解释只显示一次，也只计字一次。解释可为空，如 `{{@S014 |}}`，只显示来源角标。标题、代码块和图片替代文本不支持此语法，必须把引用移到正文或后续图来源说明；未闭合、跨行或不合法的标记会明确报错。

表格中的字面竖线写成 `A\|B`，显示为 `A|B`；引用标记内的分隔竖线不会被误拆成列。单格内容和说明必须能放进一页；过长会要求缩短或移到正文，不静默丢字。来源 ID 要独立书写；`XS001B` 是普通型号，恰好名为 `S001` 的型号仍应加描述避开来源 ID 歧义。

角标适合：来源补充、统计口径、方法、样本边界、推断限制。说明尽量 10–45 个汉字；长论证写回正文。`sources.json` 中缺少 ID、`display_name` 或 URL 时视为构建错误。

文末来源按首次引用顺序连续编号，格式为 `1. 来源简称｜发布者｜完整标题｜URL｜发布日期：YYYY-MM-DD｜访问日期：YYYY-MM-DD`；学术材料附 DOI、论文页或正式出版信息（如有）。正文、图表、图谱和图注引用必须与文末记录双向一一对应。

## Markdown 约束

- 第一行 `# 报告标题`，构建器将其用于封面并从正文隐藏；
- 可在标题后写 `> 研究截面：...｜范围：...｜对象类型：...`；
- 使用 `##`、`###`、`####` 组织章节；
- 使用标准 Markdown 表格、列表、引用、粗体和本地图片；
- 正文必须适量使用 `**加粗**`；受控换色语法为 `[[blue:关键判断或数据]]`、`[[green:正向信号]]`、`[[purple:概念或方法]]`、`[[red:已证实风险]]`，渲染时同时加粗。每个主要章节至少有一处真正关键的信息强调，每段不超过 1–2 处，不整段换色；
- 图片替代文本写 `图 N｜结论型标题`，构建为 8.5pt 深蓝粗体图注；下一行用 `<span class="figure-source">来源：机构/作者，年份；来源 ID；许可或截图日期。</span>`，构建为 7.2pt 灰色来源说明；二者均与 10.5pt 深灰正文明确区分；
- JPEG/PNG 产品图、照片和界面截图按约 78% 正文宽度居中；由 `visuals.json` 生成的 SVG 数据图、时间线、矩阵和知识图谱维持全宽，不套用插图缩放；
- 只使用相对路径；本地图片格式为 JPEG、非交错 8-bit PNG 或由视觉规范生成的 SVG；
- 不留下工具 token、占位 URL、TODO、图表源码或远程图片。

## 叙事型研究文风

### 应保留

- 叙事驱动：转折前有铺垫，选择后有结果与新约束；
- 节奏变化：长短句交替，关键判断可单独成段；
- 层层剥开：现象 → 表面解释 → 深问 → 证据支撑的判断；
- 知识自然带入：在故事中解释背景，不开“科普专区”；
- 敢下判断：先摆事实，承认主观性，主动写反证；
- 文化/历史升维：只在机制真正相似时连接，不硬凑；
- 回环：前文细节在交汇或结尾完成因果闭合。

### 读者流二遍改写

第一遍完成证据稿，锁定事实、判断、反证和来源 ID；第二遍只优化叙事顺序、段落长度、转场与措辞，不改变任何事实或引用。以非虚构书稿为主，用轻度公众号节奏推动阅读：每个小节自然经历“具体事实或场景 → 核心问题 → 证据展开 → 作者判断 → 下一节桥梁”，不得虚构场景或制造廉价悬念。

一个段落只承担一个主要观点，常规段落约 80–220 个汉字，超过 300 字优先拆段。连续数据、定义和方法细节移入表格、图注或段后说明；引用放在句末或段末，相邻事实共享同一来源组时合并引用。来源编号使用紧凑上标；必要解释放在段后“说明”行，来源全名不跟随正文重复显示。每个主要章节至少有一个自然开场和一个承上启下的收束，避免连续堆叠标题、表格或结论摘要。

### 应克制

- 满篇“这玩意”“不是哥们”等强口语；
- 公众号式去标题、煽情悬念和固定互动尾部；
- 没有证据链的金句、宏大叙事和绝对化结论。

### 禁止

避免“首先、其次、最后、综上所述、值得注意的是、不难发现、赋能、抓手、打造闭环”等模板话；避免“在当今快速发展的时代”式开场；具体说产品、模型与机构，不用空泛的“某 AI 工具”。

## 对象类型适配

- 产品：版本迭代、技术路线、用户增长、关键产品决策；功能、性能、体验、价格；
- 公司：团队、融资、组织、战略转向、关键人事；商业模式、份额、营收和组织差异；
- 概念：提出者、理论/需求背景、传播、争论与演变；相近概念、阵营和适用边界；
- 人物：成长与职业轨迹、关键决策、公开言论变化；同领域人物的路线、风格、成就与影响力。

## 构建接口

跨平台单行命令：

```text
python <skill-dir>/scripts/build_report.py report.md "对象_横纵分析报告.pdf" --title "对象" --sources sources/sources.json --visual-spec data/visuals.json --html-output build/report.html --log-output build/report.build.json
```

参数：

- `--sources`：来源台账；使用编号角标和编号文献时必需；
- `--visual-spec`：共享视觉规范；Markdown 引用 SVG 时必需；
- `--author`：可选，仅写入 PDF 元数据，永不显示在封面；
- `--html-output`：可选 HTML 调试稿路径；
- `--log-output`：可选构建日志路径；
- `--html-only`：只生成调试稿；
- `--self-test`：在临时目录验证中文、英文、引用块、主章节竖条、正文强调、图注、编号映射、段后说明、来源平衡、表格、JPEG、PNG 和六类视觉。

构建器自动生成 HTML 调试稿与 JSON 日志。PDF 使用内置 ReportLab 和思源黑体，不读取系统字体或平台专属组件。

日志保留兼容字段 `status`，同时给出 `render_status` 和 `research_review_status: not_assessed`。构建成功只说明输入能被渲染并通过构建约束；来源是否真的支持结论、检索是否充分、读者是否理解仍需独立研究审查。V2.2 文件夹本身就是 skill 根，入口为 `SKILL.md`，脚本与资源同级；默认包检查只验证这一根目录。只有显式 `--root-copy <path>` 才检查副本，`--sync` 必须同时提供该目标。
